Azure collector: targeted upstream reuse plan
Reviewed 7 November 2026. No third-party source copied into the collector yet.
Our implementation uses our own mapping/adapter code; no Fix/Cartography runtime
or database is required. Official cloud SDKs remain the intended API dependency.

Priority 1: VM scale sets and instance distribution
Source: Fix resource/compute.py classes AzureComputeVirtualMachineScaleSet,
AzureAutomaticRepairsPolicy, AzureVirtualMachineScaleSetVMProfile,
AzureCapacityReservationProfile and scale-set post_process instance collection.
Reuse: translate field selectors and relationship logic into our own small mapping
functions; use its instance enumeration as a reference for a dedicated Azure SDK
collector. Do not import its Bender DSL, GraphBuilder or resource inheritance tree.
Already in ours: SKU capacity/name, repair enabled/grace/action, orchestration,
priority, reservation and health-probe references.
Add: actual instance observations, readiness evidence where available, instance
zone placement, explicit VMSS -> instance edges, upgrade/Spot restoration settings.
Do not copy Fix's omission of top-level zones. Preserve configured zones and
instance zones separately. Instance count is not checkout throughput.

Priority 1: SQL primary/standby relationships
Source: Fix resource/sql_server.py AzureSqlServerFailoverGroup,
AzureFailoverGroupReadWriteEndpoint, AzurePartnerInfo, AzureSqlServerDatabase,
and AzureSqlServer.post_process failoverGroups enumeration.
Already in ours: group role/state, partner IDs, database IDs, read/write endpoint
policy and grace, database zone redundancy and backup storage redundancy.
Add: dedicated API retrieval when Resource Graph omits child settings, explicit
partner/database relationship semantics with evidence, replication link detail.
Keep failover policy/grace fields; Cartography's models/azure/sql/failovergroup.py
is too narrow for our resilience evidence. Do not infer RTO or RPO from grace.

Priority 1: health-based routing
Source: Fix resource/network.py probe mapping and load-balancer graph connections.
Cartography intel/azure/load_balancers.py transform_backend_pools and rule
transforms provide useful separate examples of backend/pool/rule decomposition.
Already in ours: raw probes, balancing rules and pools; generic reference edges.
Add: normalized probe/pool/rule child resources with stable native identity and
explicit evidence, plus exact backend membership. Retain protocol/path/interval/
count; a configured probe is not proof that traffic is currently successful.
Cartography's reviewed module does not supply the probe detail we need.

Priority 2: capacity reservations
Source: Fix resource/compute.py AzureComputeCapacityReservationGroup and VM profile
reservation association. Already in ours: reservation references and listed IDs.
Add: reservation child enumeration, SKU/quantity/zone and allocation evidence.
Check matching scope, SKU and usable quantity. Reference presence is not a capacity
guarantee. Pricing commitments and physical capacity reservations are distinct.

Priority 2: provider wire-format handling and fixtures
Source: Cartography intel/azure/util/common.py copy_properties/rename_keys,
intel/azure/compute.py transform_vm and its Azure unit fixtures.
Reuse: reference/test cases for camelCase versus SDK snake_case responses. Prefer
one explicit wire-format boundary; do not scatter aliases through the neutral model.
Fix plugins/azure/test/files also has useful mapping fixture examples. Reuse
specific fixtures only with provenance/license review; do not run an upstream
collector or import its package merely to obtain mapping tests.

Build ourselves: gaps not solved by either reviewed implementation
- Monitor autoscaleSettings profiles/rules/schedules.
- SQL short-/long-term retention policy enumeration and backup coverage evidence.
- Uniform serviceId grouping across tagged and untagged shared dependencies.
- Neutral evidence/coverage contract and safe partial-scan reconciliation.
- Cross-cloud identity, explicit unknowns and versioned JSON export.
- Assessment and simulation: deliberately outside discovery.
Our Azure normaliser already maps several of these when supplied in inventory;
that does not prove the live Resource Graph scan returns every child resource.

Do not reuse wholesale
Fix's service stack/ArangoDB/Bender runtime or Cartography's Neo4j loaders/scheduler.
Neither upstream schema should become our public interchange format. The graph
importer is a separate consumer of cloud-inventory/1.0.0.

Acceptance before integrating any inherited mapping
A synthetic fixture with expected facts and source pointers; an actual read-only
Azure API response; denied/truncated results preserved; no silent field loss;
license/provenance recorded; no new platform runtime dependency. Validate newer
API versions independently: old API literals in copied code are not endorsements.
