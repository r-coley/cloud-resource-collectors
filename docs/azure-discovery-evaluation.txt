Azure service discovery: Fix Inventory versus Cartography
Reviewed 7 November 2026

Decision
Fix Inventory is the stronger functional fit for an Azure discovery proof of
concept. Cartography is the stronger candidate on recent repository activity,
but requires substantially more Azure resilience collection/schema development.
Do not yet adopt either as the production discovery platform. Validate Fix's
maintenance/support path and perform a read-only live Azure pilot first.
Keep the the resilience assessment engine evidence/snapshot interface independent of either product.

Method and limits
Source-level review against examples/azure-service.inventory.json.
No upstream platform was installed or executed; no Azure tenant was scanned.
This is a configuration coverage assessment, not a performance benchmark or
proof that either collector works against current Azure APIs. The synthetic
fixture is our requirements checklist, not input successfully processed by
these collectors. Presence in an API response is distinguished from retention
in the tool's model.

Our example and coverage
1. Service ownership: DEMO-SERVICE-A has tagged scale sets, load balancer and SQL
   database, plus untagged dependencies. DEMO-SERVICE-B has an App Service and
   shared plan. DEMO-SERVICE-C has no observed resources.
   Fix maps tags on VMSS and SQL database. Cartography maps tags on VMs, load
   balancers and SQL servers, but its reviewed SQL database schema omits tags.
   This matters because our database is tagged while its parent server is not.
   Neither supplies our catalogue grouping and unknown-coverage semantics.

2. VM scale sets: primary count 6, recovery count 2; automatic repair enabled,
   PT10M grace period, Replace action, regular priority and reservation reference.
   Fix explicitly maps SKU, repair policy, VM profile, priority and capacity
   reservation reference and collects scale-set instances.
   No VMSS collector/model was found in Cartography's reviewed Azure modules.
   Fix's VMSS mapping omits top-level zones; its graph builder retains source
   JSON on the local graph node, but availability in downstream exports was
   not verified. Explicit zone extraction/enrichment remains required.
   Neither configuration alone proves actual healthy instance distribution.

3. Scaling and reserved capacity: fixture autoscale min 2/max 12/default 6;
   reservation group referenced, but quantities/eligibility not proven.
   Fix has capacity reservation group collection and VMSS association mappings.
   Neither reviewed Azure implementation has Monitor autoscaleSettings
   collection. Cartography has no Azure capacity reservation collector found.
   A reservation reference does not prove enough usable reserved capacity.
   Validate region/zone, SKU, quantity and allocation separately. Spot is not
   guaranteed recovery capacity. The fixture's recovery reservation points to
   the primary region and must not be accepted as protection without checking.

4. SQL availability: zone redundancy, automatic failover, partner server and
   60-minute data-loss grace configuration.
   Fix maps database zone redundancy, failover policy, grace minutes, database
   membership and partner-server information. Its failover group connects to
   databases; explicit partner graph edges need adapter work.
   Cartography stores database zone redundancy and failover group role/state,
   but its failover group schema omits policy, grace, partners and membership.
   It cannot distinguish automatic versus manual policy from that graph alone.
   The 60-minute setting is not a measured RPO or an RTO guarantee.

5. Recovery: database geo backup redundancy and short-term retention of 14 days.
   Fix maps backup storage redundancy on SQL databases. No explicit SQL backup
   short-/long-term retention policy collector was found in either project.
   Cartography's reviewed database schema also omits backup storage redundancy.
   Restore points/recoverable databases are not equivalent to retention policy.

6. Routing: load balancer backend references and HTTPS /ready probe, 5-second
   interval and two probes.
   Fix maps probe protocol/path/interval/count and network relationships.
   Cartography collects load balancers, backend pools and balancing rules;
   probe configuration collection was not found in its reviewed LB module.
   Neither graph establishes real application health or successful checkout.

7. Estate graph and operations
   Both support multiple clouds and graph-based inventory. Fix's sample compose
   uses fixcore/fixworker and ArangoDB (plus Prometheus); Cartography uses Neo4j
   and scheduled collector execution. Both need an adapter into our JSON.
   Resource timestamps and cleanup are useful but insufficient: we must retain
   per-subscription/API permission failures, collection completeness and evidence
   timestamps so missing data never becomes an assertion that protection exists.
   Neither was benchmarked at 4,000 service services. Collect by subscription,
   then group by serviceId; do not make 4,000 independent estate-wide scans.

Recommended next experiment
1. Confirm the maintained Fix distribution/support route and supported Azure
   versions. A stale open-source branch is a material ownership cost.
2. Run Fix read-only in a non-production Azure subscription with known examples.
3. Export its actual graph and compare field-by-field with authoritative Azure
   responses and our fixture checklist, including denied permissions/deletions.
4. Add targeted Azure enrichment for zones, autoscale and backup retention;
   prove serviceId grouping includes untagged/shared dependencies.
5. Feed evidence into the existing snapshot interface; assess patterns with
   unknowns explicit. Do not automatically mark a discovered model simulation-ready.
6. If Fix's maintenance route is unacceptable, choose Cartography only with an
   explicit budget for VMSS/reservation collectors and SQL/probe schema additions.

Acceptance checks for the pilot
- Preserve serviceId on the SQL database, not merely its parent server.
- Preserve VMSS 6/2 counts, repair settings, priority and reservation IDs.
- Preserve explicit zones; leave missing recovery placement unknown.
- Preserve Automatic policy, partner/database IDs and grace 60.
- Preserve retentionDays 14 and backup redundancy Geo.
- Preserve probe /ready, HTTPS, interval 5 and count 2.
- Report denied/truncated collection and unsupported resources explicitly.
- Never infer throughput, guaranteed reservation coverage or RPO from these facts.
